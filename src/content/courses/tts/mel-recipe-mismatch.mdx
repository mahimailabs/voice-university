An 80-bin mel can have the right shape and still mean the wrong thing to a vocoder. Here, four versions of one recording show what happens when feature settings change.

## Feature Contract

It is the full list of settings that turns audio into a [mel spectrogram](/learn/100x/tts/mel-spectrogram): sample rate, FFT size, hop, number of mel bins, frequency range, mel scale, filter normalisation, magnitude or power, and log compression. A vocoder learns one recipe, and only that one.

Ours is the recipe of the pretrained [speechbrain/tts-hifigan-ljspeech](https://huggingface.co/speechbrain/tts-hifigan-ljspeech) vocoder, copied from its model card. Every stage of the build uses this one dictionary, so [the acoustic model we trained](/learn/100x/tts/train-tts-model-from-scratch) learns exactly what the vocoder expects:

```python
MEL_ARGS = dict(
    sample_rate=SR,
    hop_length=HOP,
    win_length=None,
    n_fft=1024,
    n_mels=80,
    f_min=0.0,
    f_max=8000.0,
    power=1,
    normalized=False,
    norm="slaney",
    mel_scale="slaney",
    compression=True,
)
```

`SR` is 22,050 and `HOP` is 256. `power=1` means the magnitude spectrogram. `compression=True` applies a natural log, `log(clamp(x, 1e-5))`. None of this is a universal standard, and the defaults in popular libraries disagree with it.

## Mismatch Results

It depends entirely on which setting is wrong. On LJ001-0009, by log-spectral distance to the original (lower is closer, 80 dB floor):

| Mel fed to the vocoder                 | Log-spectral distance |
| -------------------------------------- | --------------------- |
| Correct recipe (copy synthesis)        | 12.3 dB               |
| fmax 11,025 Hz instead of 8,000 Hz     | 12.9 dB               |
| librosa dB-scaled power mel            | 14.7 dB               |
| HTK mel scale, no Slaney normalisation | 33.2 dB               |

This is one clip and one vocoder, and log-spectral distance is not a perceptual score. It measures how far each spectrum drifted; how a listener would rate the result is a separate question. Press play on each and judge for yourself.

## Filter Differences

Because the mel scale decides which frequencies every bin means, while fmax only stretches where the filters end. A vocoder reads bin positions as meaning.

The HTK and Slaney formulas map hertz to mels differently, so with 80 filters over the same range, filter 20 in one covers a different band from filter 20 in the other. The vocoder has learned "energy in bin 20 means a harmonic around here". Move the bins and it is rendering the wrong spectrum. Dropping Slaney normalisation compounds it, because that normalisation divides each filter by its bandwidth, so every bin's magnitude changes too.

Moving fmax from 8,000 to 11,025 Hz keeps the scale and count and spreads the 80 filters over a wider band. Each bin shifts, but less, and LJSpeech carries little energy up there: on this clip, 1.9% of the energy is above 8 kHz. That is our best explanation for the 0.6 dB change, and we have not tested it further.

The librosa variant sits between the two. We passed it the vocoder's `n_fft` 1024, hop 256 and 80 mels, and it still changes several things at once: power instead of magnitude, decibels (`10 log10`) instead of a natural log, an 80 dB floor below the peak, and librosa's default fmax, which is half the sample rate. Its values are on a different scale from what the vocoder expects, yet it scored 14.7 dB. We did not isolate which of those changes cost the most.

## Compatibility Checks

Run [copy synthesis](/learn/100x/tts/what-is-a-neural-vocoder) with your recipe on a real clip before you train anything. If the vocoder cannot render mels computed from real audio, it will not render your model's predictions either.

The check that catches this bug in practice is a default. torchaudio's [MelSpectrogram](https://docs.pytorch.org/audio/stable/generated/torchaudio.transforms.MelSpectrogram.html) defaults to the HTK scale with no normalisation and power 2. librosa (0.11) defaults to Slaney with Slaney normalisation, power 2, `n_fft` 2048 and hop 512. Write the recipe out in full, as above, and never rely on either library's defaults matching a vocoder.

A shape check belongs in the pipeline too. Our data prep recomputes each clip's mel and asserts its frame count equals the length the aligner's durations add up to, so a hop or sample rate slip fails loudly before training.
