## Evaluation Sets

Two parts: sentences like the training data that the model never saw, and sentences built to break it.

**Held-out.** The 45 validation clips' transcripts, 821 words. The model never trained on them. They come from LJSpeech's normalised text column, so none contains a digit. Because these clips also guided checkpoint selection, this is validation evidence, not an independent final test. The pretrained Piper and HiFi-GAN training splits have not been established here, so “held-out” applies only to our acoustic model.

**Hard.** 16 sentences, 177 words, written for the inputs a voice agent gets wrong: an order number, an account number, times, money, a phone number, years, a dose, "Dr.", ordinals, a digit-by-digit code, two uncommon names and one long agent-style sentence. A few, as they sit in the harness:

```python
HARD = [
    "your order number is 48213",
    "the total comes to $129.50",
    "call us on 555 0192 before 6",
    "Dr. Okonkwo will see you at 10:30",
    "please confirm the code 7 4 9 1",
    "Saoirse and Nguyen both signed the form",
    # ...
]
```

The hard set is where the design work goes. Use your own traffic: the numbers, names and phrasings your agent will read, and the longest turn it will produce.

## System Variants

Eight rows: seven system rows and one real-audio ASR control.

- **The tiny model at steps 1,100, 1,650 and 2,200**, with text passed through our symbol set as-is. `encode` keeps letters, apostrophe and space, so digits are dropped.
- **The same three checkpoints after a minimal normaliser** (num2words for numbers, ordinals, years, money and times, plus "Dr." to "doctor" and "%" to "percent").
- **Piper en_US-ljspeech-medium**, which does its own text processing through espeak-ng. It was warmed up with one call before timing.
- **The real LJSpeech recordings** of the held-out set, transcribed the same way, to measure the transcriber itself.

One transcriber for everything: [faster-whisper](https://github.com/SYSTRAN/faster-whisper) base.en, int8, beam size 5, on a 4-core cloud container with no GPU. Scoring is corpus-level, total errors over total reference words, so a long sentence counts for more than a short one:

```python
def agg(kind):
    rs = [r for r in rows if r["kind"] == kind]
    # corpus-level WER: total errors / total reference words
    errs = sum(r["wer"] * r["ref_words"] for r in rs)
    return {"n": len(rs), "words": sum(r["ref_words"] for r in rs), "wer": errs / sum(r["ref_words"] for r in rs)}
```

Each row's WER comes from [jiwer](https://github.com/jitsi/jiwer), after both reference and transcript pass through the same `words()` function: numbers to words, lowercase, punctuation stripped.

## Measured Results

WER in percent. RTF is synthesis seconds divided by audio seconds over all 61 sentences.

| System                                 | Held-out WER | Hard WER | RTF   |
| -------------------------------------- | ------------ | -------- | ----- |
| Real LJSpeech recordings (ASR control) | 1.7          | n/a      | n/a   |
| Piper en_US-ljspeech-medium            | 4.0          | 8.5      | 0.037 |
| tiny @ step 1,100                      | 26.3         | 66.1     | 0.272 |
| tiny @ step 1,100 + normaliser         | 26.3         | 32.2     | 0.253 |
| tiny @ step 1,650                      | 19.7         | 64.4     | 0.247 |
| tiny @ step 1,650 + normaliser         | 19.7         | 35.6     | 0.248 |
| tiny @ step 2,200                      | 22.9         | 59.3     | 0.238 |
| tiny @ step 2,200 + normaliser         | 22.9         | 31.6     | 0.223 |

Four readings:

- **The control.** Whisper scores 1.7% WER on the real recordings. Its errors on synthetic audio can differ, so do not subtract 1.7 points or treat it as a lower bound.
- **Piper against ours.** 4.0% held-out against our best 19.7%: about five times fewer errors. Piper's RTF of 0.037 here is about 27x faster than real time; on the three probe sentences in [end-to-end TTS](/learn/100x/tts/end-to-end-tts-vits) it was 0.052, about 19x. Our model sits at 0.22 to 0.27, with the vocoder taking most of that.
- **The normaliser.** It changes nothing on held-out, which has no digits, and roughly halves the tiny model's hard-set WER (64.4% to 35.6% at step 1,650).
- **Checkpoint choice.** Step 1,650 is best on held-out, which matches the earlier three-probe result. Step 2,200 is best on the hard set, raw (59.3%) and normalised (31.6%). If your traffic is mostly numbers, the ranking from clean text would pick the wrong checkpoint.

## Scoring Limits

Three, and each applies to every hard-set number above.

1. **The normaliser grades itself.** The reference text is built by the same normaliser that feeds the "+ normaliser" rows. It reads the phone number "555 0192" as "five hundred and fifty five one hundred and ninety two", and because the reference says the same, that reading scores as correct. A person expecting a phone number would mark it wrong. The same normaliser reads "0042" as "forty two", losing the leading zeros an account number needs.
2. **Piper's "7491" is a scoring artifact.** Piper read "please confirm the code 7 4 9 1". Whisper wrote "7491", our scorer turned that into "seven thousand four hundred and ninety one", and Piper was charged 50% on a sentence it probably said correctly. We did not listen-verify every row.
3. **Name spellings are partly Whisper's doing.** Piper's audio came back as "Akonko" (Okonkwo), "Sersha" (Saoirse) and "Nuyin" (Nguyen). A recogniser's spelling of rare names is part of that, and the transcript alone does not show that Piper mispronounced them.

So the hard-set column overstates some errors and hides others. Read it as a ranking of our systems on these sentences, with the failures quoted in [hallucinations](/learn/100x/tts/tts-hallucinations) as the detail.

## Regression Gates

We did not wire this harness into CI. The design we would use:

- **Store a baseline** per system: held-out WER, hard WER, RTF, and the per-sentence transcripts.
- **Rerun on every change** to the model, the voice, the normaliser, the runtime or the transcriber.
- **Fail on a margin, per set.** A rise in either set's WER beyond what reruns of the unchanged system produce. Set that margin from your own repeated runs; we ran each system once, so we have no noise figure to give you.
- **Keep the real-audio control.** If it moves, inspect recognizer settings, preprocessing and runtime changes before attributing other differences to TTS.
- **Diff transcripts.** When a gate fails, the useful artifact is the sentence that changed, which the stored rows give you.

<Practice label="Starting your own harness">
  Take 40 or so held-out lines and write 15 or so sentences from your real traffic with numbers,
  names and your longest turn. Run the real recordings through your transcriber first to establish
  an ASR control, then every candidate voice through the same code path.
</Practice>
