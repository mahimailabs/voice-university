After 1,650 steps, 200 seconds of training on a 4-core cloud container with no GPU, a 1,231,185-parameter model was asked to say "please call me back when you have a moment". Whisper transcribed the result as "please pull me back when you have a moment."

One word wrong, from a model that started as random numbers 200 seconds earlier. The full run took 268 seconds, and its last checkpoint did worse.

On this page you get the whole thing: the model class, the length regulator, the loss, the training log, and the audio at each of four checkpoints, with the transcription error rate next to each. Every excerpt is from the training script as we ran it.

## What does "from scratch" cover here?

The acoustic model, the stage that turns text into a mel spectrogram, starts from random weights and is trained by us. The two stages around it are pretrained, and each has a reason.

First, the **aligner** (torchaudio's MMS, from [forced alignment](/learn/100x/tts/forced-alignment-tts)) tells us how many mel frames each letter lasts. Learning alignment jointly is a large part of what makes attention-based TTS slow and fragile to train; taking durations from an aligner removes that job from the model. The **vocoder** is the pretrained LJSpeech HiFi-GAN from [speechbrain/tts-hifigan-ljspeech](https://huggingface.co/speechbrain/tts-hifigan-ljspeech) (Apache-2.0). A vocoder is a much bigger training job than this model, and copy synthesis in unit 1 already showed it can render LJSpeech mels. Our model's only job is to predict the vocoder's exact mel recipe.

Our training set is small on purpose: 413 clips (0.74 h) that passed the alignment filter, plus 45 validation clips. Symbols are the 26 letters, apostrophe and space. Punctuation is dropped.

## What does a FastSpeech-style model look like in code?

It is an encoder over characters, a duration predictor, a length regulator that stretches the character sequence to mel length, and a decoder over mel frames. Its layers, from the model class:

```python
class TinyTTS(nn.Module):
    def __init__(self, d: int = 128, heads: int = 2, ff: int = 256, layers: int = 2, dec_layers: int = 4, n_mels: int = 80):
        # ...
        self.emb = nn.Embedding(len(SYMBOLS), d, padding_idx=0)
        self.enc = nn.ModuleList([Block(d, heads, ff) for _ in range(layers)])
        self.dur = nn.Sequential(  # predicts log(1 + frames) per symbol
            nn.Conv1d(d, d, 3, padding=1), nn.ReLU(), nn.Dropout(0.1),
            nn.Conv1d(d, d, 3, padding=1), nn.ReLU(), nn.Dropout(0.1),
            nn.Conv1d(d, 1, 1),
        )
        self.dec = nn.ModuleList([ConvBlock(d) for _ in range(dec_layers)])
        self.out = nn.Linear(d, n_mels)
```

The encoder blocks are transformer layers with a convolutional feed-forward, the shape the [FastSpeech paper](https://arxiv.org/abs/1905.09263) uses. The decoder blocks are plain residual 1-D convolutions. The length regulator is three lines:

```python
def regulate(self, x, durs):
    """Repeat each symbol's vector durs[i] times (the length regulator)."""
    seqs = [torch.repeat_interleave(xi, di, dim=0) for xi, di in zip(x, durs)]
    lens = torch.tensor([len(s) for s in seqs], device=x.device)
    return nn.utils.rnn.pad_sequence(seqs, batch_first=True), lens
```

In training, `durs` are the aligner's durations. At inference they come from the duration predictor, rounded and clamped to at least one frame. [Duration prediction](/learn/100x/tts/tts-duration-prediction) covers why that one substitution makes the model unable to skip a word.

## Which loss trains a TTS acoustic model?

Two terms, added with equal weight: an L1 distance between predicted and real mel frames, and a mean squared error on log durations. Both are masked so padding does not count.

```python
m, logd, mpad = model(ids, durs)
valid = ~mpad
mel_loss = (F.l1_loss(m, mels, reduction="none").mean(-1) * valid).sum() / valid.sum()
spad = ids != 0
dur_loss = (F.mse_loss(logd, torch.log1p(durs.float()), reduction="none") * spad).sum() / spad.sum()
loss = mel_loss + dur_loss
```

Two details matter. The target mels are standardised with the training set's mean and standard deviation (-5.41 and 2.09 in our `prep.json`), and the model's output is un-standardised before it goes to the vocoder. And durations are predicted as `log(1 + frames)`, so a letter held for 40 frames and one held for 4 contribute errors on a comparable scale.

The optimiser is AdamW at a learning rate of 1e-3, warmed up linearly over the first 1,000 steps and then decayed linearly towards a 5% floor. Gradients are clipped at norm 1.0.

## How long does it take to train a TTS model on a CPU?

On our setup, 268 seconds for 2,200 steps at batch 8, which is 8.2 steps per second. The first version was far slower.

That first design used a transformer decoder over mel frames. A 7-second clip is about 600 mel frames, and attention over 600 frames dominated each step: we saw several seconds per step, measured while the aligner was sharing the CPU, so treat that as an order of magnitude only. Swapping the decoder for convolutions, whose cost grows linearly with length, made it fast. Attention stayed in the encoder, where sequences are around 100 characters.

The run was 2,200 steps at batch 8 with a checkpoint every 550. Here is the training log it wrote, selected lines:

The errors on the kept checkpoint are substitutions ("pull" for "call"). On these three probes Whisper returned the same number of words as the input every time, which is what a duration-driven model should do. What it cannot do is read digits: `encode` keeps only letters, apostrophe and space, so "call 911" loses the number without an error. [Hallucinations](/learn/100x/tts/tts-hallucinations) returns to that.
