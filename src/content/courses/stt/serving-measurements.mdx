The saved run includes a warm forward-pass timing for one 1.315-second example. The median was about 0.495 milliseconds over 30 repetitions with four CPU threads. Feature extraction, decoding, queueing, networking and audio capture are excluded.

This number is useful for reproducing a small compute experiment. It cannot establish how long a caller waits, how many streams a server supports, or the cost of a production recognizer.

## Timing Boundaries

| Measurement | Start → end |
| --- | --- |
| Feature work | Waveform available → features ready |
| Encoder work | Feature tensor → frame log probabilities |
| Decode work | Frame probabilities → output string |
| Segment delay | Relevant audio boundary → final segment delivered |
| Reply delay | Caller finishes → first audible response |

Use a monotonic clock for durations. Warmups, batch size, thread count and the timed examples belong in the report. Accelerator work needs appropriate synchronization; the recorded experiment uses CPU execution.

## Capacity Experiment

Do not divide one forward-pass duration into a concurrency promise. Run realistic arrival patterns with complete preprocessing, decoding and per-stream state. Measure queue growth, memory and tail delays, then increase load until the declared targets fail.

Our downloadable lab does not implement an HTTP server, real-time transport or stateful streaming encoder. Those are explicit next engineering tasks, not features implied by the word “serving.”

## Final Deliverable

You now have a small trained recognizer, source and split manifests, decoded predictions, checkpoint-selection evidence, noise probes and a prefix replay. Your final report should state the observed errors as clearly as the successful predictions.
