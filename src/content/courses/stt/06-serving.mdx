## 18. Self-hosted inference: quantisation, batching, streaming

Owning a recognition model means serving it, and the three levers are the same as the TTS course with the constraints inverted: recognition input arrives in real time from live calls, so the serving stack is shaped by concurrent audio streams rather than by synthesis requests.

**Quantisation.** Recognition encoders tolerate 8-bit weights well as a rule; verify below that with the harness, watching the hostile-SNR and entity slices first, because quantisation damage lands on the hard cases before the easy ones.

**Batching across streams.** A live call produces a trickle of audio, far below what saturates a GPU. Throughput comes from batching frames across many concurrent calls into each forward pass. The knob trades the same way as TTS: batch window up, cost per audio-hour down, per-call latency up. For interactive agents the batch window must stay inside the finalisation budget from lesson 12, which caps how far the cost lever turns.

**Streaming state.** Each live stream carries model state between chunks, encoder caches, decoder history, biasing context. Serving is therefore stateful: sizing is bounded by concurrent streams and their memory, not just by compute, and stream affinity has to survive scaling events without dropping mid-call state.

<Pull>
  The capacity number that matters is concurrent real-time streams per GPU at your latency budget,
  measured with the harness running against the loaded server, not offline real-time factor on a
  benchmark clip.
</Pull>

<Practice>
  Every serving change, quantisation level, batch window, chunk size, reruns the harness as a gate.
  The failure mode of serving optimisation is identical to TTS: a cost win that is quietly an
  accuracy regression on the slice you were not watching.
</Practice>

## 19. Latency, cost per audio-hour, and the API crossover

Self-hosting recognition is justified by one comparison: your amortised cost per audio-hour at acceptable latency versus API per-minute pricing at your volume. Building the honest version:

**Cost side.** GPU hourly rate divided by concurrent streams served at your latency budget, from the previous lesson's measured number. Add what APIs hide: warm headroom for call peaks, redundancy across zones, and the engineering time to operate it. Recognition adds one line TTS does not have: calls are continuous streams, so capacity is provisioned for peak concurrency, and utilisation outside peak hours is where the spreadsheet quietly dies.

**Latency side.** Finalisation latency and partial stability at p95, from your region, under production concurrency, with scaling events included. A stack that autoscales into cold model loads mid-afternoon has a p95 problem that never appears in a load test that starts warm.

**The crossover.** Below it, APIs win on every axis that is not compliance. Above it, typically at sustained six-figure monthly minutes with honest utilisation, ownership wins on cost, and it wins on something else the spreadsheet undercounts: the adaptation stack from unit 5 is only fully available on a model you serve yourself.

<Pull>
  Run the calculation with measured stream capacity and honest peak-to-average ratios, before
  hardware is committed. The most common self-hosting mistake is not technical. It is a utilisation
  assumption off by three.
</Pull>

</Practice>

## 20. On-prem, in-region, and keeping audio inside the boundary

The closing lesson, and for a class of buyers the deciding one: caller audio is regulated in ways synthesised audio never is, because it contains what people actually said, names, health information, card numbers, spoken into a system that must answer for where those words went.

**In-region deployment** satisfies residency requirements with the same stack deployed inside the named jurisdiction, and with the media path audited end to end: trunk ingress, recognition, storage of transcripts and recordings, all in-region. Recognition adds the transcript to the audit surface, the text is as regulated as the audio it came from, and lesson 7's redaction pipeline becomes a production component, not a training-data tool.

**On-premise and air-gapped** deployment tightens everything from lessons 18 and 19: fixed hardware, update-by-process, monitoring that works without external calls, and model choice constrained to what the installed GPUs serve at the required stream count. The adaptation stack travels too: adapters trained outside, validated with the harness, delivered as artifacts through the client's own process.

**Licensing** gates the whole design, as it did for TTS: the base model's license governs commercial use, and an on-prem delivery is a distribution. Permissively licensed open recognition models make this stack possible at all; research-only weights make it a liability wearing a demo.
