A web service deploys by replacing instances behind a balancer, and nobody notices. Try that on a voice fleet and every node you replace takes its live calls with it.

The framework knows how to wait. Your supervisor usually does not. A 30-second kill timer in front of a worker holding a ten-minute call ends that call mid-sentence, whatever the drain setting says.

## Drain Behaviour

Draining means a node stops taking new calls, lets its existing calls end on their own, and only then exits. Every zero-downtime voice deploy is this one primitive applied per tier.

Both LiveKit components drain natively on a termination signal. What differs is how long they wait and what can cut the wait short.

| Component            | Signal                   | While draining                                                       | Exits when                             |
| -------------------- | ------------------------ | -------------------------------------------------------------------- | -------------------------------------- |
| Agent worker         | SIGTERM, SIGINT          | Accepts no new jobs; running jobs continue                           | Jobs finish, or `drain_timeout` passes |
| LiveKit server (SFU) | SIGTERM, SIGINT, SIGQUIT | Active rooms run and admit participants; joins to new rooms rejected | Every participant has disconnected     |

Sources: [agent server options](https://docs.livekit.io/agents/server/options/) and [downscaling and draining](https://docs.livekit.io/transport/self-hosting/distributed/) in the LiveKit docs.

## Shutdown Timeouts

A worker in production (`start`) mode drains on SIGTERM: it stops accepting jobs and waits for running ones, up to `drain_timeout`. The default is one hour. The deploy only works when every timer above it is longer.

Two decisions make it real.

**The drain timeout must exceed your longest reasonable call.** A five-minute timeout with calls that can run to ten minutes kills the tail mid-sentence, so if you have lowered it, raise it back above your call length:

```python
from livekit.agents import AgentServer

# Longest reasonable call: 10 minutes. Drain for 15.
server = AgentServer(drain_timeout=900)  # seconds in Python
```

**The supervisor must be told to wait longer than the drain.** A systemd unit or Kubernetes pod with a 30-second kill timer overrides the framework's patience with its own, and the drain you configured never actually runs. Both end in SIGKILL.

```ini
# systemd unit: must exceed drain_timeout
[Service]
TimeoutStopSec=960
```

```yaml
# Kubernetes pod spec: must exceed drain_timeout
spec:
  terminationGracePeriodSeconds: 960
```

`TimeoutStopSec` is documented in [systemd.service](https://man7.org/linux/man-pages/man5/systemd.service.5.html). The order to check is: longest call, then `drain_timeout`, then the supervisor timeout, each longer than the last.

This is also where [the agent shutdown leak](/learn/100x/livekit/livekit-agent-shutdown-leak) stops being theory: a worker that never reports job completion never finishes draining, and your deploy pipeline hangs on a bug you shipped weeks earlier. If a drain takes exactly `drain_timeout` every time, suspect that before you suspect long calls.

## Termination Hooks

To drain an SFU node, stop new room placement on it, let existing rooms end naturally, then terminate. A multi-node deployment with Redis makes this workable, because new rooms route to the remaining nodes while this one empties (see [multi-node LiveKit with Redis](/learn/100x/livekit/livekit-multi-node-redis)).

LiveKit server does the first two steps itself on SIGTERM. The risk is the layer above it terminating the instance early, and on an Auto Scaling group a termination lifecycle hook holds the instance in a wait state while it drains:

```bash
aws autoscaling put-lifecycle-hook \
  --lifecycle-hook-name drain-calls \
  --auto-scaling-group-name sfu-asg \
  --lifecycle-transition autoscaling:EC2_INSTANCE_TERMINATING \
  --heartbeat-timeout 900
```

The hook does not execute the drain by itself. Wire its event to an instance-side agent or orchestration handler with permission to send heartbeats and complete the lifecycle action. Then use this sequence:

1. The hook fires and the instance enters its wait state.
2. On the instance, stop the LiveKit service so it receives SIGTERM and starts draining. The server exits when its last participant leaves, so the unit's `TimeoutStopSec` must also outlast your longest call.
3. Watch the node's active-call count, the same custom metric from [autoscaling on active calls](/learn/100x/livekit/voice-autoscaling-signal). If calls are still running near the heartbeat timeout, extend it with `aws autoscaling record-lifecycle-action-heartbeat`.
4. When the node reports zero calls, release it:

```bash
aws autoscaling complete-lifecycle-action \
  --lifecycle-action-result CONTINUE \
  --lifecycle-hook-name drain-calls \
  --auto-scaling-group-name sfu-asg \
  --instance-id "$INSTANCE_ID"
```

Two limits from the [AWS lifecycle hook docs](https://docs.aws.amazon.com/autoscaling/ec2/userguide/lifecycle-hooks.html) matter here. The heartbeat timeout ranges from 30 to 7,200 seconds, and termination hooks have a finite global timeout too; repeated heartbeats cannot wait forever. A timeout can allow termination while calls remain. The drain guard should prevent routine termination above zero, but cannot guarantee survival of a crash, expired hook or forced termination. Test those recovery paths separately.

## Rolling Replacement

Roll one node at a time and drain each one fully before terminating it. Your longest call sets the deploy clock. The CI pipeline does not.

  calls, then replace it.

1. **Pick the traffic trough.** Deploy when the fewest calls are in flight.
2. **Hold headroom for the roll.** The fleet is one node short throughout, so the remaining nodes must carry the trough without crossing the per-node cap from [the capacity model](/learn/100x/livekit/voice-capacity-model).
3. **Drain one node.** Signal it, stop new work, wait out its longest call.
4. **Confirm zero.** The node reports zero active calls before anything terminates it.
5. **Replace and verify.** The new node registers and takes calls before the next one drains.
6. **Know the duration.** Measure how long a drain actually takes on your traffic, and budget the deploy as that number times the node count.

## Deploy Exercise

Test the drain path under load before you need it: deploy during a load test and count dropped calls, and the number you get is either zero or a defect of the kind covered in [silent failures](/learn/100x/livekit/voice-silent-failures). A controlled test limits the customer impact. Finding it during a campaign costs the campaign.

The stakes are bigger than one deploy. Voice fleets that cannot deploy safely stop deploying, and then the real cost arrives: the fix that waits three weeks for a maintenance window. Drain discipline is what lets infrastructure that holds phone calls keep the deploy cadence of a web service.
