Here is what one concurrent call cost on a production LiveKit fleet we measured:

| Resource           | Per concurrent call                        |
| ------------------ | ------------------------------------------ |
| Media ports        | 18.3, linear across three saturation steps |
| Worker memory, PSS | 122 MB                                     |
| File descriptors   | 38.4                                       |

Three numbers. From them we predicted the media tier's ceiling near 550 calls before any test got there, picked the instance family for the workers, and set the descriptor limit in the service file. By the end of this lesson you will know how to produce a table like this for your own fleet, and the arithmetic that turns it into node counts.

## Why fleet-level metrics fail a voice system

Fleet metrics answer whether the system is healthy on average, and nothing about a voice fleet fails on average. A node runs out of ports at a specific call count. A call either carries audio or it does not. The questions that matter for sizing are per call: what does the next call cost, and which budget does it exhaust first?

So the accounting has one shape everywhere. Measure each resource per call, as a slope against concurrency. Count failures as instances. Everything else in [unit 4](/learn/100x/livekit#unit-4) and [unit 5](/learn/100x/livekit#unit-5) is built on those two habits.

## What a slope gives you that a reading cannot

A slope is the marginal cost of one more call, fitted across many samples. It does three jobs a point reading cannot.

1. **It separates baseline from marginal cost.** An idle worker pool already holds memory for the parent process and its warm children. Divide total memory by call count at one moment and that baseline leaks into your per-call figure. The fit puts it in the intercept instead.
2. **It extrapolates.** You can compute where a budget runs out without driving the system there.
3. **It detects nonlinearity.** The day the slope bends is the day something changed, and you want to know which day that was.

The method we used: sample every ten seconds through a ramp, then fit by least squares against the active call count. The full memory measurement is in [PSS vs RSS for agent workers](/learn/100x/livekit/livekit-agent-memory-pss-rss). On Linux each input is one read away. PSS comes from `/proc/PID/smaps_rollup` ([kernel docs](https://docs.kernel.org/filesystems/proc.html)), and the open descriptors of a process are the entries in `/proc/PID/fd` ([proc_pid_fd(5)](https://man7.org/linux/man-pages/man5/proc_pid_fd.5.html)):

```bash
# PSS in kB for one process
grep '^Pss:' /proc/$PID/smaps_rollup

# open file descriptors for one process
ls /proc/$PID/fd | wc -l
```

Sum those across every process in the pool at each sample, record the active call count next to it, and fit. Python's standard library does the fit:

```python
from statistics import linear_regression

# calls[i] and pss_mb[i] were sampled at the same moment
slope, intercept = linear_regression(calls, pss_mb)
print(f"{slope:.0f} MB per call, {intercept:.0f} MB baseline")
```

## Worked example: from slopes to ceilings

Divide each node budget by its slope and you get a ceiling. With our numbers:

| Resource         | Slope         | Node budget           | Arithmetic               | Ceiling         |
| ---------------- | ------------- | --------------------- | ------------------------ | --------------- |
| Media ports      | 18.3 / call   | 10,001-port RTP range | 10,001 / 18.3            | ~550 calls      |
| Worker PSS       | 122 MB / call | 30 GB                 | 30,000 / 122             | ~245 calls      |
| File descriptors | 38.4 / call   | systemd default 1,024 | 100 calls x 38.4 = 3,840 | limit must rise |

Each row drove a decision. The port row said the SFU would stop carrying audio near 550 calls, well before any load test reached that step, and [the port exhaustion lesson](/learn/100x/livekit/livekit-port-exhaustion) shows the test that confirmed it. The PSS row said memory was not the worker constraint, so CPU was, and the instance family changed. The descriptor row said a hundred concurrent calls would want roughly 3,840 descriptors against a default of 1,024, so the limit was raised with a measurement behind it.

None of these needed the fleet to fail first. That is the payoff of measuring slopes early: the ceiling shows up in a spreadsheet long before it can show up in an incident.

## Count failing calls, never the ratio

The companion habit is for failures. Count the calls that exhibited the defect. Do not report a fleet-wide ratio.

On one run the fleet received 99.8% as many RTP packets as it sent, while half the calls in a subset carried nothing. Both statements were true at once. An aggregate ratio cannot distinguish every call being slightly lossy from some calls being completely dead, so the number that should have raised the alarm read as proof of health. [The load test that reported 100% success](/learn/100x/livekit/voice-silent-failures) tells that story in full.

Before you put any number on a dashboard, ask one question: can this number hide a bimodal failure? Averages, ratios, and percentiles over the whole fleet all can. Per-call counts cannot. That is why the alerting gate became "zero calls with zero inbound packets" instead of any threshold on any ratio.

  headroom per resource all fall out of that table.
