A caller dials in. The trunk answers, the room exists, your agent has joined, and every dashboard is green.

The caller hears nothing.

Where do you look first? LiveKit is one product and five processes, and each one fails in its own way. By the end of this page you will know what each process does, which of the two planes it lives on, and which one to suspect for the three symptoms you will actually get paged for.

## What are the five parts of LiveKit?

A production LiveKit deployment is five cooperating processes: the server (an SFU), the SIP service, your agent workers, Redis, and TURN. On a laptop you only see two of them, which is why the first production deploy surprises people.

| Process       | What it does                                                   | Runs on your laptop?        |
| ------------- | -------------------------------------------------------------- | --------------------------- |
| Server (SFU)  | Receives each participant's media once and forwards it         | Yes, `livekit-server --dev` |
| SIP service   | Bridges phone calls into rooms                                 | Only if you set it up       |
| Agent workers | Your code: STT, LLM, TTS, turn detection                       | Yes                         |
| Redis         | Room state and message routing between nodes                   | No, a single node hides it  |
| TURN          | Relays media for clients that cannot reach the server directly | Rarely needed locally       |

Every later lesson is about one row of that table.

## The SFU is where capacity runs out

The server is a Selective Forwarding Unit. It takes each participant's audio once and forwards it to everyone who should hear it, with no mixing and no transcoding in the common path.

That design is why it is cheap per call, and also why it matters so much: every RTP packet of every call passes through here. Capacity is won or lost on this machine.

You would expect CPU to be the first ceiling. It is UDP ports. A voice call holds roughly 18 of them, and when the configured range runs out, new calls still connect and simply carry no audio. [Unit 5](/learn/100x/livekit#unit-5) is that whole story, starting with [why media servers run out of ports before CPU](/learn/100x/livekit/livekit-port-exhaustion).

## The SIP service speaks telephony for you

The SIP service is a separate process that talks SIP and RTP to telephony carriers on one side and joins rooms as an ordinary participant on the other. A phone caller shows up in your room as a participant it created.

It has its own addressing, its own port ranges, and its own failure modes. One of those cost us three days. Carrier audio needs `symmetric_rtp: true`, because NAT rewrites the source port and the address in the SDP is not where the caller can actually be reached. The full diagnosis is in [the one-way audio lesson](/learn/100x/livekit/livekit-one-way-audio-nat).

## Agent workers, Redis and TURN

These three are easy to forget until one of them is missing.

**Agent workers** are your code. Python or Node processes register with the server, take a job when a room needs an agent, and run one process per active call. Everything AI lives here: STT, LLM, TTS and [turn detection](/learn/components/turn-detection). LiveKit's own docs describe [how agents connect and receive jobs](https://docs.livekit.io/agents/); [unit 3](/learn/100x/livekit#unit-3) covers what that process model does under load.

**Redis** is coordination. Multi-node deployments use it for room state and for routing messages between nodes, and the SIP service and workers use it to find the cluster. A single-node laptop hides it completely. Production requires it, and [the multi-node lesson](/learn/100x/livekit/livekit-multi-node-redis) shows the wiring.

**TURN** is the relay for clients whose network blocks a direct WebRTC path. It can be embedded in the server or run alongside it, and in practice you cannot skip it, because some fraction of real users are always behind a hostile NAT.

## Two planes: signalling and media

Every call runs on two planes at once. Signalling and coordination go through the server and Redis, while audio goes directly between clients, the SFU, and the SIP service.

The split matters because the planes fail independently. The ports each one needs are listed in LiveKit's [ports and firewall reference](https://docs.livekit.io/transport/self-hosting/ports-firewall/): signalling is one TCP port you can put behind a load balancer, while media is a UDP range that has to reach the node directly.

  and every dashboard will still read green.

## Which part owns the symptom?

Triage by plane first, then by process. Three symptoms cover most pages:

| Symptom                            | Plane      | Suspect first              | Read next                                                              |
| ---------------------------------- | ---------- | -------------------------- | ---------------------------------------------------------------------- |
| Call never connects                | Signalling | Server or SIP service      | [SIP self-hosting](/learn/100x/livekit/livekit-sip-self-hosted)        |
| Connected, but silent or one-way   | Media      | Ports, firewall, NAT, TURN | [Calls that carry no audio](/learn/100x/livekit/voice-silent-failures) |
| Connected, audio flows, agent mute | Worker     | Agent worker process       | [Worker lifecycle](/learn/100x/livekit/livekit-agent-worker-lifecycle) |

The middle row is the dangerous one. No counter reports it, so you only find it if you go looking. Knowing which plane owns a symptom saves the hour you would otherwise spend on the wrong one.
