Calls connected. Signalling was clean. The caller sent RTP and received nothing.

It took us three days to find. With what follows, it should take you ten minutes.

You'll see why fixing the advertised address is necessary and still not enough, what NAT does to the source port, how to confirm it in a packet capture, and the one config line that fixes it.

## The first fix was right, and it changed nothing

The SDP answer advertised a private address, so the cause looked clear: the media server was telling the caller to send audio to an address the caller could not reach. Fix the advertised address, fix the call.

On the LiveKit SIP service, that part of the fix is `use_external_ip: true` (or an explicit `nat_1_to_1_ip`), and LiveKit's own [SIP troubleshooting guide](https://docs.livekit.io/reference/telephony/troubleshooting/) names it as the most common cause of one-way audio when self-hosting.

We fixed the address. The audio stayed one way.

## What the SDP cannot know

An SDP answer says: send media to this address and this port. The caller obeys. The packets arrive having passed through NAT, which rewrote the source address and, critically, the source port.

The media server then replies to the address and port in the caller's SDP, which is what the caller believed about itself before NAT touched the packets. The caller cannot actually be reached there.

Here is what that looks like with example addresses:

| What                              | Address and port     |
| --------------------------------- | -------------------- |
| Caller's SDP says "send to me at" | `10.0.4.17:16384`    |
| RTP actually arrives from         | `198.51.100.23:9012` |
| Server replies (default)          | `10.0.4.17:16384`    |
| Server replies (symmetric RTP)    | `198.51.100.23:9012` |

Correcting the advertised address fixes half the problem and leaves the other half, because NAT rewrites the port too. There is no address you can put in an SDP that survives a translation the sender cannot see.

## The one-line fix: symmetric RTP

Tell the SIP service to reply to where the packets actually came from:

```yaml
# livekit sip config.yaml
symmetric_rtp: true
```

With it set, the service sends RTP back to the observed source address and port of the caller's media, whatever the SDP said. Asterisk, FreeSWITCH and every session border controller do the same thing under different names, because it is the mechanism that makes carrier traffic work at all.

The name comes from [RFC 4961](https://www.rfc-editor.org/rfc/rfc4961), which defines symmetric RTP as sending and receiving a stream on the same address and port. An endpoint that behaves that way is one you can safely reply to at its observed source.

## How to confirm it in a packet capture

Put the SDP and the RTP side by side. On the SIP host, capture while you place a test call:

```bash
tcpdump -n -i any -w call.pcap udp port 5060 or udp portrange 10000-20000
```

Open the file in Wireshark and compare two things:

1. The `c=` address and `m=audio` port in the caller's SDP.
2. The source address and port of the RTP packets that arrive from the caller.

If they differ, NAT is rewriting them, and replying to the SDP values will send your audio nowhere. If the service's outbound RTP goes to the SDP values while inbound RTP arrives from somewhere else, you are looking at this bug.
