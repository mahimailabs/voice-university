A caller on hotel Wi-Fi opens your app. UDP is blocked. So is every TCP port except 443.

Without a relay path that session never starts, and the failure is invisible in your metrics because no session was ever established. Corporate firewalls and certain mobile carriers do the same. TURN is that relay path.

By the end you'll have the TURN section of `livekit.yaml`, a certificate plan that survives renewal, the five firewall rules that must match config, and a way to test the relay on purpose.

## How does WebRTC decide when to use TURN?

WebRTC tries candidates in order of preference: direct UDP, then TCP fallback, then a TURN relay. Most users connect directly. The relay exists for the remainder. In production, the remainder is never zero.

That ordering is ICE, specified in [RFC 8445](https://www.rfc-editor.org/rfc/rfc8445), and the relay itself is TURN, [RFC 8656](https://www.rfc-editor.org/rfc/rfc8656): the client allocates an address on the TURN server, and media flows through it. Relayed traffic over TLS on port 443 looks like ordinary HTTPS to a firewall, which is exactly why it gets through the networks that block everything else.

## The TURN section of livekit.yaml

LiveKit embeds a TURN server, so this is configuration, not a new deployment. Enable it, give it a domain, and put a TLS certificate on it, using the keys below from LiveKit's [deployment guide](https://docs.livekit.io/transport/self-hosting/deployment/) and config sample:

```yaml
turn:
  enabled: true
  # must match the TLS certificate
  domain: turn.example.com
  # advertised to clients: set 443 when no load balancer sits in front
  tls_port: 443
  # optional TURN/UDP (default 3478)
  udp_port: 3478
  cert_file: /etc/livekit/turn.crt
  key_file: /etc/livekit/turn.key
```

Three details catch people:

- `tls_port` defaults to 5349, and that is the port clients are told to use. Leave it there without a load balancer and the restrictive networks you enabled TURN for still can't reach it.
- TURN needs its own domain and its own certificate, separate from the signalling domain.
- If the same IP already terminates signalling TLS on 443, two listeners can't share it. Give TURN its own address, or put a layer 4 load balancer in front and set `external_tls: true` so LiveKit expects unencrypted traffic on `tls_port` while still advertising it as TURN/TLS.

Some networks now pass UDP on 443 because of QUIC, so if that fits your callers, `udp_port: 443` enables TURN/UDP there.

## Certificates that renew themselves

The signalling endpoint and the TURN endpoint both need valid TLS from a trusted authority. Self-signed certificates do not work. Terminate at the server with certificates you renew automatically, and make sure the renewal job reaches both.

An expired certificate produces the worst class of outage. Web clients fail. Phone calls through the SIP path keep working. Put together, those two facts point everywhere except the certificate, which is why the expiry date of both certificates belongs on a dashboard next to call volume.

## The complete firewall picture: five rules

Every rule pairs with one config value, and the pair must match exactly. Here is the full set for a stack with the SFU, TURN and the SIP service, using the defaults from earlier lessons:

| Rule             | Port        | Protocol | Must match                                   |
| ---------------- | ----------- | -------- | -------------------------------------------- |
| Signalling       | 443         | TCP      | TLS terminator in front of `port: 7880`      |
| ICE TCP fallback | 7881        | TCP      | `rtc.tcp_port`                               |
| TURN over TLS    | 443         | TCP      | `turn.tls_port`                              |
| SFU media        | 50000-60000 | UDP      | `rtc.port_range_start`, `rtc.port_range_end` |
| SIP media        | 10000-20000 | UDP      | `rtp_port` in the SIP service config         |

Two 443 rows means two addresses (or a load balancer), per the section above. Add `3478/UDP` if you enable TURN/UDP, and `5060` for SIP signalling from [the SIP lesson](/learn/100x/livekit/livekit-sip-self-hosted); LiveKit's [ports and firewall reference](https://docs.livekit.io/transport/self-hosting/ports-firewall/) lists every port with its config key.

## Test the relay path on purpose

Force TURN in a test client and confirm audio flows; with the LiveKit JS SDK, that means restricting ICE to relay candidates when you connect:

```ts
await room.connect(url, token, {
  rtcConfig: { iceTransportPolicy: 'relay' },
});
```

If audio flows both ways, the relay works end to end: domain, certificate, port and firewall. If it doesn't, you've found the failure before a caller did. The relay is the path you never use on your own network and your users use daily, which makes it the path that breaks without anyone on the team noticing.

## What relay traffic costs you

Relay traffic crosses the TURN node twice, in and out, so it costs bandwidth twice. Relayed calls also come from your worst-network users, and once volume grows, the TURN node's egress and its placement both matter.

Instrument what fraction of connections relay. The selected ICE candidate pair in WebRTC stats reports a candidate type of `relay` when a session goes through TURN. A rising relay share is an early signal of a network-quality shift in your caller population. Nothing else will surface it.
