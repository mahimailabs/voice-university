You launch an instance, start the server, and a test client connects in seconds. Signalling works. Then the first real call joins and nobody hears anything.

On EC2 that is nearly always one of two things. The server is advertising an address callers cannot reach, or the UDP port range in `livekit.yaml` and the one in the security group disagree. Neither one writes an error anywhere.

The server itself is a single Go binary with modest needs, and those two sharp edges are the whole difficulty. This page walks through the setup (instance, network, `livekit.yaml`, security group) so both places agree on day one, and sizes the port range on purpose. What happens when a node outgrows its range is its own story, told in [port exhaustion before CPU](/learn/100x/livekit/livekit-port-exhaustion).

## Which EC2 instance and network does LiveKit need?

Use a compute-optimised instance in a public subnet with a public IP. Media forwarding is CPU and network, so memory-heavy instance families buy you nothing, and LiveKit's [deployment guide](https://docs.livekit.io/transport/self-hosting/deployment/) recommends compute-optimised types too.

The public IP is the part people try to avoid. Media must reach the machine directly: RTP is UDP flowing to one specific node, so placing the SFU's media ports behind a load balancer does not work, and the balancer adds nothing but confusion. Signalling is different. Port 7880 is plain HTTP and WebSocket, and it can sit behind a load balancer or reverse proxy that terminates TLS.

Attach an [Elastic IP](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/using-instance-addressing.html). An ordinary EC2 public IP is released when the instance stops and a new one is assigned on start, and every client and carrier you configured is then pointing at an address you no longer own.

## Which ports does LiveKit need open on AWS?

Three port groups, two of them plain TCP. This is where deployments fail:

| Port            | Purpose                                                                      |
| --------------- | ---------------------------------------------------------------------------- |
| 443 / 7880 TCP  | Signalling, API, WebSocket                                                   |
| 7881 TCP        | ICE over TCP fallback                                                        |
| 50000-60000 UDP | The RTP media range: one config, one security group rule, sized deliberately |

As inbound security group rules, that looks like this:

| Protocol | Port range  | Source                             | Purpose                      |
| -------- | ----------- | ---------------------------------- | ---------------------------- |
| TCP      | 443         | `0.0.0.0/0`                        | Signalling over TLS          |
| TCP      | 7880        | Your load balancer, or `0.0.0.0/0` | API and WebSocket            |
| TCP      | 7881        | `0.0.0.0/0`                        | ICE over TCP                 |
| UDP      | 50000-60000 | `0.0.0.0/0`                        | RTP media                    |
| UDP      | 3478        | `0.0.0.0/0`                        | Embedded TURN/UDP (optional) |

The TURN row only applies if you enable the embedded TURN server; [the TURN lesson](/learn/100x/livekit/livekit-turn-server-setup) covers when you need it. If the SIP service runs on the same instance, it brings its own signalling port and its own RTP range, both covered in [self-hosted SIP](/learn/100x/livekit/livekit-sip-self-hosted). LiveKit's [ports and firewall reference](https://docs.livekit.io/transport/self-hosting/ports-firewall/) lists every port and the config key that sets it.

With the AWS CLI, the media rule is one command:

```bash
aws ec2 authorize-security-group-ingress \
  --group-id sg-0123456789abcdef0 \
  --protocol udp --port 50000-60000 \
  --cidr 0.0.0.0/0
```

## The `livekit.yaml` lines that matter

Five keys under `rtc` decide whether media flows. Here they are with the values from LiveKit's recommended production config:

```yaml
port: 7880
rtc:
  tcp_port: 7881
  port_range_start: 50000
  port_range_end: 60000
  # Discover the public IP via STUN and advertise it to clients.
  use_external_ip: true
  # Only if STUN picks the wrong address: set use_external_ip to false
  # and give the public IP (your Elastic IP) explicitly.
  # node_ip: 203.0.113.10
keys:
  your-api-key: your-api-secret
```

Start the server with `livekit-server --config /etc/livekit.yaml`. The full list of keys is in LiveKit's [config-sample.yaml](https://github.com/livekit/livekit/blob/master/config-sample.yaml). Once you add a second node, a `redis` block joins this file; [the multi-node lesson](/learn/100x/livekit/livekit-multi-node-redis) covers it.

## The RTP range lives in two places

The RTP range in `livekit.yaml` and the UDP range in the security group must match exactly. If they drift, the server hands out ports the firewall blocks.

Here is why that hurts. Security groups only have allow rules, so a media port the firewall does not permit is dropped before it reaches the machine, and nothing records the drop. The server never sees the packet, so it cannot log it. The call connects, and carries silence.

That failure mode gets a full lesson in [unit 5](/learn/100x/livekit#unit-5), because it found us at 612 concurrent calls.

## How big should the RTP port range be?

Size it from ports per call, and write the result down as a capacity number. Our measurement, across three saturation steps: 18.3 media ports per call, dead linear.

Here is the arithmetic with the default range:

| Quantity                      | Value                                 |
| ----------------------------- | ------------------------------------- |
| Default range, 50000 to 60000 | 10,001 ports                          |
| Ports per call (measured)     | 18.3                                  |
| Calls at exhaustion           | 10,001 / 18.3, which is near 550      |
| Ports at 400 calls            | 400 x 18.3 = 7,320 (73% of the range) |

A 10,001-port range is exhausted near 550 calls. That is also roughly where the 70% CPU line arrives, which is exactly why the port ceiling hides behind it. [Port exhaustion before CPU](/learn/100x/livekit/livekit-port-exhaustion) shows why we settled on 400 calls per node, with 27% port headroom.

Whatever range you configure is a capacity decision. If you widen it, widen the security group first and the server config second, so there is never a moment where the server offers ports the firewall drops.

## Advertise the address callers can actually reach

The server must announce the public IP that clients can reach. The private address the instance sees is useless to a caller outside the VPC. EC2 maps the public address onto the instance's private one through one-to-one NAT, so the machine only sees its private VPC address on its own interface.

`use_external_ip: true` makes the server discover the public address with STUN and advertise that; if discovery ever picks the wrong one, turn it off and set `node_ip` to the Elastic IP by hand. Behind EC2's NAT, this line decides whether media flows at all. Its subtler cousin, where the address is right and the port is still wrong, is [the one-way audio lesson](/learn/100x/livekit/livekit-one-way-audio-nat).
