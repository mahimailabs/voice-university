Every run came back FAIL. Including the runs where nothing was wrong.

The same reports printed a capacity figure twelve times too low and a failure count that repeated the same facts over and over. The fleet was fine in all three cases. The tool was wrong, and we wrote the tool.

Bugs like these survive for a long time because nobody suspects the ruler. When a load test disagrees with expectations, the first instinct is to debug the system under test, and every hour spent there is an hour the report goes unquestioned. Here are the three defects, what each looked like from the outside, and the fix we shipped. Use these three cases as checks on your own harness.

| Defect                     | What the report showed      | Root cause                                     | Fix                                          |
| -------------------------- | --------------------------- | ---------------------------------------------- | -------------------------------------------- |
| Verdict that always failed | FAIL on every run           | Resource check sampled during teardown         | A defined settle period before sampling      |
| Capacity twelve times low  | "Carries at least 51 calls" | One generator's concurrency read as the node's | Refuse to derive capacity from parallel rows |
| Repeating failure count    | 1,423 gate rows             | Each fact counted once per generator process   | Count distinct subject and value pairs       |

The numbers below are saved case-study results. The original raw run bundle is not included here, and this review did not rerun the fleet experiment.

## Cleanup Timing

The top-line verdict read FAIL on every run, passing or not, because a resource check was measuring normal cleanup and calling it a regression.

The check sampled memory and file descriptors about a minute after the last call ended and compared them against the run's baseline. In that run, a minute was still inside teardown: processes are exiting, descriptors are closing, memory is on its way back down. Any snapshot taken in that window looks like a leak.

We fixed it by making the settle period part of the check itself and sampling only after it. The inputs were never the problem. Memory and descriptor counts read from `/proc` ([smaps_rollup](https://docs.kernel.org/filesystems/proc.html) for PSS, [the fd directory](https://man7.org/linux/man-pages/man5/proc_pid_fd.5.html) for descriptors) were accurate, but they were read at the wrong moment.

This one matters more than it looks. Once a headline is always wrong, people stop reading it, and then it cannot warn them about anything. A gate that never passes is worse than no gate at all.

## Generator Scope

The report printed "carries at least 51 calls" for a run that carried 612 across the fleet, because it mistook one generator process for the whole rig.

Several generator processes ran in parallel, each holding its own share of the calls, and 51 was the concurrency of a single one of them, and the tool took that process's number for the node's capacity. Anyone sizing from the figure would have over-provisioned twelve to one.

The tool now refuses to derive per-node capacity from parallel generator rows, and it reports what it measured and no longer prints what it inferred.

A derived number has to know the shape of the rig that produced it, so if your [load testing rig](/learn/100x/livekit/voice-agent-load-testing) runs several generators in parallel, every aggregation downstream needs to know that too.

## Duplicate Events

A report showed 1,423 gate rows for a run that had about 169 distinct things to report, because every measurement was counted once per generator process.

The count therefore scaled with how many generators happened to run, not with anything the fleet did: double the generators and the failure list would double, with no change in the system under test.

The case report deduplicated repeated observations by subject and value. For a general event log, include stable call or job ID, check ID and observation window so genuinely separate failures are not collapsed. A re-render of an old run now reads lower and is more accurate, which is a strange thing to ship and the right thing to ship.

## Report Audit

When a report and a fleet disagree, the bug can be in either one. Give your measurement stack one adversarial pass where you assume the tool is the defendant:

1. **Separate measured from derived.** Mark every number in the report as one or the other. Derived numbers are where all three of our bugs lived.
2. **Let derived numbers fail loudly.** If the tool cannot compute a figure correctly from the rows it has, it should say so and print nothing.
3. **Put the settle period in the check.** Any before-and-after comparison needs a defined wait after load stops.
4. **Give every aggregation an identity.** Deduplicate repeated observations by stable identity and window, without merging separate calls that share an error value.
5. **Check the clock.** Grouping by end time instead of start time [inverted a failure curve](/learn/100x/livekit/load-test-time-bucketing) on the same project.

Ours needed three convictions before the reports could be trusted, and every capacity number in [the capacity model](/learn/100x/livekit/voice-capacity-model) depends on that trust.
