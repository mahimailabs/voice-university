At 612 calls, one media node needed 11,120 UDP ports. Its configured range held 10,001. The calls connected anyway, and they carried no audio. CPU read 75.7%.

Every capacity model we have seen for a media server is built on CPU: measure CPU per call, pick a target utilisation, divide. It is the obvious approach, and it was wrong for the SFU tier we were sizing. By the end of this lesson you will know how many ports a call used on that tier, why the CPU model looks right until it fails, and the order to change things in when you raise per-node capacity.

## How many UDP ports does a LiveKit call use?

On the fleet we measured, each concurrent call held 18.3 media ports on the SFU node, and the count grew in a straight line with calls. We counted media ports in use on a single node across three saturation steps:

| Calls on the node | Media ports | CPU   |
| ----------------- | ----------- | ----- |
| 204               | 3,738       | 35.4% |
| 408               | 7,422       | 56.5% |
| 612               | 11,120      | 75.7% |

That is 18.3 ports per call, dead linear. The range those ports come from is set in the server config: LiveKit's [ports and firewall reference](https://docs.livekit.io/transport/self-hosting/ports-firewall/) lists it as `rtc.port_range_start` and `rtc.port_range_end`, and the defaults in the [sample config](https://github.com/livekit/livekit/blob/master/config-sample.yaml) are:

```yaml
rtc:
  port_range_start: 50000
  port_range_end: 60000
```

Both ends are inclusive, so that is 10,001 ports. Divide by 18.3 and the range is exhausted near 550 calls.

## Why the CPU model looks right until it fails

The 70% CPU line also arrives near 550 calls. Two ceilings, measured independently, land in the same place.

That coincidence is the trap. Size on CPU and your predicted ceiling matches the real one, so the model appears to work. It keeps appearing to work right up until the day something moves one ceiling and not the other: a new instance type, a codec change, a lighter build of the server. Then the two separate, and the one you are not watching arrives first.

## What happens past the port range: connected calls, no audio

At the 612 step the node went past its configured range, 11,120 ports wanted against 10,001 available. Calls still connected. They carried no audio.

There was no error, no rejection, no CPU spike. Signalling succeeded because it does not need a media port. The result is connected calls carrying silence while every gauge you are watching reads normal. This is the same failure shape as [one-way audio behind NAT](/learn/100x/livekit/livekit-one-way-audio-nat), with a different cause, and it is one of the failure modes collected in [the load test that reported 100% success](/learn/100x/livekit/voice-silent-failures).

## Why a bigger instance does not help

More vCPU does not add ports. A larger instance moves the CPU ceiling up and leaves the port ceiling exactly where it was. The only thing scaling up achieves is making the no-audio failure arrive ahead of the CPU alarm.

<Pull>
  Size on ports, not CPU, and leave headroom in the resource that fails without an error. We settled
  at 400 calls per node, 27% port headroom, below the 550 the CPU curve would have allowed.
</Pull>

## How to raise per-node capacity safely

Change the firewall first and the RTP port range second, in that order. A media port the firewall does not permit is dropped before it reaches the machine, and nothing records the drop. If you widen the range in `livekit.yaml` first, the new ports are handed out to calls and the packets never arrive.

1. **Widen the inbound UDP rule** in the security group (or whatever firewall fronts the node) to cover the new range. See the AWS reference for [security group rules](https://docs.aws.amazon.com/vpc/latest/userguide/security-group-rules.html).
2. **Then change `rtc.port_range_start` and `rtc.port_range_end`** to match the rule exactly, and restart the node.
3. **Recompute the ceiling**: range size divided by your measured ports per call, then take your headroom off the top.
4. **Rerun a saturation step** above the old ceiling and confirm every call received inbound packets.

The setup side of the same rule, config range and firewall range matching exactly, is in [deploying LiveKit on AWS](/learn/100x/livekit/self-host-livekit-aws).
