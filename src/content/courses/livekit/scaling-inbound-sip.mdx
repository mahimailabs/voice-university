The question was how to spread 500 concurrent inbound calls across several SIP nodes. The obvious answer is a load balancer.

It does not work, because the balancer is never asked.

By the end of this lesson you'll know who actually decides where an inbound call lands, how to get spreading and failover without building anything, and when a SIP proxy is worth the extra tier (and what it still leaves exposed).

## Why a load balancer does nothing for inbound SIP

Your carrier decides where inbound calls go. It sends INVITEs to the Origination URIs configured on the trunk, one per address you gave it, so the distribution decision is made in the carrier's console before any packet reaches your infrastructure.

A carrier does not resolve a name and connect to whatever answers, the way a browser does. It works through the list you configured. Put one URI on the trunk and every call goes to one node, no matter how many nodes you run behind it.

Here is what the three possible configurations actually produce:

| Origination URIs on the trunk        | What you get                                   |
| ------------------------------------ | ---------------------------------------------- |
| One URI                              | Every call on one node. Others sit idle.       |
| Several, same priority, equal weight | Calls spread across nodes, with failover.      |
| Several, different priorities        | Active and standby. One node takes everything. |

The second and third rows look almost identical in a carrier config screen. Only one of them spreads load.

## What each SIP node needs before the carrier can use it

Every SIP node needs its own stable public address, and every node you add is another trunk entry. Scaling out is an address plus a change in the carrier account, made by whoever owns that account.

That has two practical consequences:

1. **No ephemeral addresses.** A node that comes up on a new public IP after a replacement is a node the carrier cannot reach until someone edits the trunk. Allocate a fixed address per SIP node; the carrier already treats it as the origination target when you [run the LiveKit SIP service yourself](/learn/100x/livekit/livekit-sip-self-hosted).
2. **Adding a node is not free.** Autoscaling the SIP tier the way you [autoscale media nodes on active calls](/learn/100x/livekit/voice-autoscaling-signal) only works if the trunk already lists the address the new node will take.

On the LiveKit side, the [inbound trunk and dispatch rule](https://docs.livekit.io/telephony/accepting-calls/inbound-trunk/) are API objects rather than per-node config, so adding a node does not mean editing them.

## Where a Kamailio or OpenSIPS proxy fits

A SIP proxy lets the carrier point one URI at the proxy while the proxy distributes calls to your nodes internally. Node count stops being the carrier's business.

It also does two things a carrier URI list does not do on its own. It can select a node on real load, and it can drop a dead node by probing it with keepalives. Kamailio's [dispatcher module](https://kamailio.org/docs/modules/stable/modules/dispatcher.html) is the usual building block: weighted and load-based distribution across a destination set, with SIP OPTIONS probes that mark an unresponsive destination inactive.

## What a SIP proxy does not fix: media

Kamailio and OpenSIPS are signalling proxies. They never touch the audio. Your media server answers with its own address in the SDP, so RTP flows from the carrier straight to that node and bypasses the proxy entirely.

This is the part people miss. The proxy collapses N trunk entries into one. It does not collapse N public addresses into one, because the carrier still needs to reach every media node directly. (SIP carries the session setup, per [RFC 3261](https://www.rfc-editor.org/rfc/rfc3261); the addresses the audio actually uses live in the SDP body it carries.)

If the goal is private media nodes, you have to pair the proxy with a media relay. That combination is what a session border controller actually is here. Then every call's audio passes through one relay, which must itself be sized, monitored and scaled, and which becomes a single point of failure for calls that previously had none. The same port arithmetic from [lesson 19](/learn/100x/livekit/livekit-port-exhaustion) now applies to a box that carries everyone's audio.

## Direct URIs or a proxy tier: how to choose

At four or five nodes, the direct path is simpler and it works. The proxy earns its place in two situations:

- the carrier cannot hold multiple Origination URIs on one trunk, or
- node count makes URI management a standing chore, which in practice is around eight nodes.

Below that, a proxy adds a component to operate without removing any public addresses.

## Check this first

Before building any of it, open the carrier console and read the Origination URI list on the trunk. If it has one entry, that is the whole problem. Adding the other nodes at the same priority and equal weight is a two-minute fix, and it gets you spreading and failover without a new tier.
